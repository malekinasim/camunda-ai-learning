# Project brief: تفویض task از انسان به عامل AI در موتور BPM

مخزن فعلی: github.com/malekinasim/camunda-ai-learning
وضعیت در: اکتبر ۲۰۲۶ (آخرین commit: ۱۶ سپتامبر ۲۰۲۶)
هدف‌ها: (۱) کامل کردن پروژه، (۲) نوشتن مقاله برای Substack گروه Data & AI Stockholm، (۳) استفاده در رزومه و مصاحبه‌های نقش‌های BPM

---

## ۱. ایده‌ی اصلی

همان user task در مدل BPMN می‌تواند به یک انسان یا به یک عامل AI برسد، **بدون اضافه کردن شاخه‌ی جداگانه‌ی AI به مدل فرایند**. تصمیم اینکه task به چه کسی برسد در یک DMN decision table گرفته می‌شود، نه در کد ثابت. تصمیم‌های نهایی و حساس دست انسان می‌ماند.

ریشه‌ی مسئله از تجربه‌ی واقعی: در سیستم‌های فرایندی بزرگ، کارتابل‌ها پر از taskهای تأیید ساده می‌شوند که وقت کاربران را می‌گیرند.

---

## ۲. وضعیت فعلی کد

**Stack:** Java 17، Spring Boot 3.5، Camunda 8 Java SDK 8.7، Zeebe / Tasklist / Operate 8.6 (Docker)، Elasticsearch، PostgreSQL، Spring Data JPA، Docker Compose، Claude API

**فرایندها:**

| فرایند | رفتار |
|---|---|
| `resume-review-process` | یک service task رزومه را با Claude امتیاز می‌دهد. امتیاز ۵۰ یا بیشتر → بررسی انسانی؛ کمتر → پایان فرایند. |
| `hr-review-with-delegation-process` | یک start execution listener رکوردهای تفویض را از دیتابیس می‌خواند و DMN تعیین می‌کند user task «HR review» به انسان برسد یا به `agent-bot`. |

**اجزای اصلی کد:**
- `ResolveAssigneeListener`: رکوردهای تفویض فعال را می‌خواند (قانون مخصوص task بر قانون عمومی اولویت دارد؛ چند قانون هم‌اولویت یا مقصد خالی رد می‌شود) و `resolve-assignee.dmn` را اجرا می‌کند.
- `resolve-assignee.dmn`: decision table با hit policy از نوع UNIQUE و دو قانون: تفویض فعال → `delegateTo`، وگرنه → `defaultAssignee`.
- `AgentTaskCompletionPoller`: هر ۱۰ ثانیه به Tasklist لاگین می‌کند، taskهای فعال `agent-bot` را پیدا می‌کند، رزومه را با Claude امتیاز می‌دهد، نتیجه را **قبل از** complete کردن ذخیره می‌کند (تا در تلاش بعدی دوباره Claude صدا زده نشود) و task را complete می‌کند.
- `ClaudeScoringService`: خروجی مدل را اعتبارسنجی می‌کند (score صحیح ۰ تا ۱۰۰، decision برابر APPROVED یا REJECTED، reason غیرخالی). خروجی نامعتبر باعث شکست تلاش می‌شود، نه امتیاز صفر.
- `DelegationController`، `JobController`، `ResumeController`، `ResumeReviewController`، `StartProcessController`: REST API برای ساخت آگهی، رزومه، رکورد تفویض و شروع فرایند.
- تست‌ها: `ResolveAssigneeListenerTest`، `AgentTaskCompletionPollerTest`، `ClaudeScoringServiceTest`.

**محدودیت‌های فعلی (طبق README):**
1. فقط برای **یک instance** از برنامه طراحی شده؛ distributed lease یا exactly-once ندارد.
2. بین Tasklist و PostgreSQL تراکنش مشترک نیست؛ نتیجه‌های نامعلوم برای بررسی بعدی باقی می‌مانند.
3. نقش، نوع task و assignee پیش‌فرض در کد Java ثابت (constant) هستند.
4. DMN فقط بین «انسان پیش‌فرض» و «مقصد تفویض» انتخاب می‌کند و هنوز **قوانین واقعی کسب‌وکار** را ندارد.
5. نتیجه‌ی فرم انسانی به جدول `ResumeReview` برنمی‌گردد.
6. user task از نوع job-worker است، نه native Camunda user task (`zeebe:userTask`).
7. احراز هویت با cookie و حساب پیش‌فرض Tasklist است و CSRF در محیط محلی خاموش است.
8. نسخه‌ی SDK (8.7) با نسخه‌ی imageهای Docker (8.6) یکی نیست.

## ۳. قدم اول: بررسی کد (قبل از هر تغییر)

برای اینکه هر بخش را بتوانی در مصاحبه و مقاله توضیح بدهی:

- [ ] اجرای کامل محلی با Docker Compose و دنبال کردن یک instance در Operate
- [ ] توضیح دادن به زبان خودت: listener دقیقاً چه زمانی اجرا می‌شود و چرا start execution listener انتخاب شده
- [ ] توضیح دادن: worker چطور task را پیدا، قفل و complete می‌کند
- [ ] توضیح دادن: چرا راه‌حل فعلی فقط برای یک instance درست است و برای چند instance چه لازم است
- [ ] مرور مفاهیم DMN: hit policyها (UNIQUE، FIRST، PRIORITY، COLLECT) و عبارت‌های FEEL
- [ ] نوشتن لیست چیزهایی که در کد نمی‌فهمی یا با آن موافق نیستی

## ۴. نیازمندی‌های پیشنهادی (پیش‌نویس، برای تصمیم‌گیری)

**باید داشته باشد (Must):**
- **R1. DMN واقعی:** تصمیم تفویض بر اساس چند ورودی کسب‌وکار، مثلاً نوع task، سطح ریسک، مبلغ یا اهمیت، و میزان اعتماد به عامل برای این نوع task.
- **R2. سه حالت خروجی:** انسان انجام بدهد / عامل پیشنهاد بدهد و انسان تأیید کند / عامل خودش complete کند (فقط برای موارد کم‌ریسک).
- **R3. بازگشت به انسان:** اگر عامل مطمئن نبود، خروجی نامعتبر داد یا خطا خورد، task به انسان برگردد.
- **R4. ردپا (audit):** برای هر task ثبت شود چه کسی یا چه چیزی تصمیم گرفت، با چه دلیلی، و کدام قانون DMN اعمال شد.
- **R5. تنظیمات بیرون از کد:** نقش‌ها، نوع taskها و assigneeها از دیتابیس یا تنظیمات خوانده شوند، نه constant.

**بهتر است داشته باشد (Should):**
- **R6.** نتیجه‌ی فرم انسانی به دیتابیس برگردد، تا تصمیم انسان و عامل قابل مقایسه باشند.
- **R7.** یک سناریوی دوم غیر از رزومه، نزدیک به تجربه‌ی واقعی (مثلاً تأیید درخواست‌های ساده‌ی پرتکرار).
- **R8.** یکسان کردن نسخه‌های Camunda (SDK و Docker).

**شاید بعداً (Could):**
- **R9.** مهاجرت به native Camunda user task.
- **R10.** اجرای امن با چند instance.
- **R11.** همین الگو روی یک موتور قدیمی (Camunda 7 یا Oracle BPM) بدون migration، طبق ایده‌ی «اضافه کردن عامل به سیستم موجود».

## ۵. تصمیم‌هایی که باید بگیری

1. چه چیزی تعیین کند task به عامل برسد؟ (ورودی‌های R1)
2. انسان کجا کنترل نهایی دارد؟ (مرز بین حالت‌های R2)
3. مقاله درباره‌ی کدام است: Camunda 8، یا «اضافه کردن عامل به موتور موجود بدون migration»؟
4. سناریوی اصلی مقاله چیست؟
5. چقدر وقت داری و کدام نیازمندی‌ها در نسخه‌ی اول هستند؟

## ۶. طرح اولیه‌ی مقاله (پیش‌نویس)

1. **مسئله:** کارتابل‌هایی که با تأییدهای ساده پر می‌شوند (از تجربه‌ی واقعی)
2. **ایده:** همان مدل فرایند، تصمیم «چه کسی انجام بدهد» در DMN
3. **معماری:** BPMN + DMN + worker عامل + بازگشت به انسان (یک دیاگرام)
4. **پیاده‌سازی:** نکته‌های کلیدی کد، نه همه‌ی کد
5. **محدودیت‌ها و درس‌ها:** یک instance، تراکنش، اعتماد به خروجی مدل، کنترل انسانی
6. **قدم بعد:** همین الگو روی موتورهای قدیمی‌تر
